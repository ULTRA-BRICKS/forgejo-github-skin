# Native enhancer browser CI

`native-browser.yml` runs the repository-pinned Playwright package against production enhancer code in synthetic, native-shaped DOM fixtures. It does not run Storybook, log into Forgejo, publish a product, or establish authenticated/physical-iOS acceptance.

## Execution boundary

The existing Forgejo `ubuntu-latest` GARM pool uses ephemeral Ubuntu 24.04 guests (4 vCPU / 6 GiB each). The workflow uses at most two concurrent matrix jobs; each Playwright process uses two workers. Each job has a 25-minute limit and each test invocation a 15-minute limit. Chromium and WebKit each run 320, 440 and 1280-pixel projects. Dependencies come from `npm ci` and the installed `./node_modules/.bin/playwright`; browser system packages are installed inside the disposable guest, never on the production host. npm and tests refuse root execution.

The config reuses the mobile suite's timeout/expectation conventions. Organization, both pagination enhancers, theme-load races, release styles, search scope and native diff layout run in every project. Native header/list/repository-control and native page-layout tests run at 320/440 because they start with mobile-only controls; restoration tests resize to desktop explicitly. The 1280 projects are not renamed mobile runs. Tests that deliberately resize retain their own viewport transitions.

There is no free-form command, URL or credential input. Checkout credentials are not persisted. No production cookies, OAuth tokens or user comments belong in fixtures or artifacts. The browser cache lives inside disposable `node_modules`; no host browser installation or pruning is required.

Every matrix job uploads `.qa/` through the SHA-pinned Forgejo-compatible v3 artifact protocol, even after test failures. Artifacts contain the checked-out source SHA, JSON/HTML reports, and failure screenshots/traces. Retention is 14 days. Download the artifact from the job's Actions run; treat it as regression evidence, not live production proof. A failed upload fails the job rather than claiming evidence was retained.

## Resource-safe feature checkpoints

Work only in the source lane's own worktree. Never copy another worker's actively edited tree. Git-based CI cannot execute uncommitted source: the owner must first make an honest checkpoint using the normal review and commit hooks. A checkpoint records incomplete work; it is not a release-ready commit or permission to merge.

1. Reconcile the lane's task, staged diff and current owner. Keep the existing branch/worktree and exact before-change evidence. Run only locally permitted non-browser checks; stop if a resource guard refuses them. Do not disguise a denied suite as separate commands.
2. The owner stages only their coherent source/test changes. Use `review diff --staged --task '#63' -C /absolute/lane/worktree --commit </dev/null` for the organization lane (header: `'#61'`; keyboard: `'#67'`; other parity work uses its actual task). `--commit` is review-cli's supported incomplete checkpoint path and runs real commit hooks. Record pending browser acceptance and any known failing regression explicitly. If review or hooks refuse, stop: there is no authorized bypass or uncommitted upload path in this workflow.
3. Once this CI-only change is merged, fetch and merge current `origin/main` into the lane's checkpoint branch using normal conflict/review gates. Alternatively the owner can take the reviewed CI-only commit onto a dedicated QA branch after coordinating its exact SHA. Do not merge another feature lane or copy its dirty tree. Keep any existing task-routing config ownership separate.
4. The native allowlist already selects `activity-density.spec.mjs` and `universal-search-header.spec.mjs` when those files exist in the checkpoint. They use production modules with local synthetic fixtures; their absent files do not create tests on main. Add any other new native fixture suite to `playwright.native.config.mjs` in the lane's own reviewed checkpoint after verifying its boundary. Do not add Storybook or authenticated/live-production suites here.
5. Push the reviewed checkpoint branch with `git push -u origin HEAD`. Open a draft with `fj pr create 'WIP: organization server regression checkpoint' --base main --head fj-goal-org-20261001 --body-file /absolute/checkpoint-pr-body.md`. The body must reference the actual ticket with `Refs #63`, list the exact source SHA, and state that native browser acceptance is pending. Header/parity owners substitute their actual branch/task/title. PR creation triggers server CI; subsequent checkpoint pushes retrigger it. No merge is authorized for these incomplete feature branches.
6. After the workflow exists on the target branch, a dedicated QA branch can instead run `fj actions dispatch native-browser.yml qa/organization-checkpoint`. This takes only a Git ref, not arbitrary shell or URL inputs. Dispatch availability must be verified against the server; a draft PR is the normal first-run path. Do not dispatch and create a PR simultaneously for the same checkpoint.
7. Use `fj actions tasks` and `fj pr status <number>` to find results. Save failing run/artifact URLs and the source SHA before the owner fixes a regression. Review and checkpoint the fix normally, push, then retain GREEN evidence for the new SHA. A configured workflow or a passing unit suite alone is not browser proof.

Local browser execution remains subject to machine resource policy. If WARN/2 blocks review as well as tests, even the first checkpoint cannot proceed until the guard naturally permits it or an already authorized review environment is available. Do not disable guards, forge receipts, use `--no-verify`, or silently claim server acceptance.
